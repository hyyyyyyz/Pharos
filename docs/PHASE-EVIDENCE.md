# 阶段记录：页面级证据

路线图第 2 项。给"论断"一个能被翻到的页码——后面三项（可溯源问答、带证据的想法、
主张与结果绑定）全部压在这一层上。

契约见 [RESEARCH_WORKFLOW.md](RESEARCH_WORKFLOW.md) §8 与 §11，关键决定的理由见
[DECISIONS.md](DECISIONS.md)。本文只记**做了什么、为什么这样做、以及哪些判断是有代价的**。

---

## 问题

`Paper.full_text` 早就有了：整篇纯文本，喂全文搜索。但它**没有页码**——提取本来是
逐页读的，在 `"\n".join(pages)` 那一步把页边界丢掉了。

于是任何引用只能精确到"这篇论文"，而契约要求的是：

```text
claim → evidence statement → paper identity → page + section → exact quote
```

---

## 存储方式：三个方案，选了被外部评审改过的那个

我原本倾向的方案是**加一列页偏移量**：`full_text` 不动，另存一个"每页从第几个字符开始"
的数组，任何字符位置都能二分出页码。理由是这样连**现有的全文搜索都能免费带上页码**。

送给 codex 评审后，这个理由被推翻了：`snippet()` 返回的是**高亮后的文本，不是字符
偏移量**。FTS 根本没告诉我们匹配在哪个位置，所谓"免费"的收益不存在。而把高亮片段
反向匹配回原文，遇到重复短语就是歧义。

第三个方案（用时再解析 PDF）被查得更死：Zotero 导入的论文 `orig_sha256=""`，
**根本没有 PDF 文件**；而且清理路径会在提交后删掉不共享的 blob。证据创建时原文件
不保证还在。

最后落地的是 `PaperChunk` 表：**一页一块**。不是固定 token 窗口——窗口边界是切分器的
产物，对读者没有意义，而"第 7 页"是他能立刻行动的东西。`ordinal` 留着，将来一页要拆
（双栏、或一页超出模型上下文）不必动页码语义。

---

## 诚实性写进了数据库，不是写进代码

`Evidence` 上两列各回答一个不同的问题：

- **`kind`——这段文字是谁写的**：原文 `quote` / 人工 `note` / 规则摘要 `rule_summary` /
  模型推断 `model_inference`。把这四种混在一起就是伪造引用，而一旦都变成面板里的灰字，
  区别就看不见了。
- **`locator`——定位有多准**：`page`（真实提取出的页码）/ `abstract_only`（从来就只有
  摘要）/ `unlocated`（文字是真的，位置不知道）。

契约里那句「页面未知时不能生成看似精确的页码」做成了 **CHECK 约束**：`page_no` 非空
当且仅当 `locator = 'page'`。

这一条为什么值得动用数据库：**一个看起来合理的页码比没有页码更糟**——它能通过审阅。
读者翻到第 7 页发现对不上，失去的不是这一条的信任，是**其余每一条**的信任。写在服务层
是约定，写在 schema 里是任何未来的写入路径都绕不过去。三种坏组合实测全被拒。

服务层再补约束表达不了的部分：

- 引文的页码**永不接受客户端传入**，只能从 chunk 上读出来
- 阅读器可以带一个 `page_hint`，但它只是待验证的出现位置：只有该页的 owner-scoped
  chunk 里确实包含同一段归一化引文时才采用。它不是 `page_no`，不能把客户端给的数字
  变成事实；因此重复引文可以保留用户实际选中的那一处。
- 选区矩形只有在 `page_hint` 验证通过时才会保存；提示页验证失败时，矩形不会附到后端
  回退选出的另一页，而是安全降级为不带矩形的 quote；引文本身仍按后端已验证的最早
  匹配页保存。
- 改引文的文字会**重新解析页码**——否则"页码留着、字换掉"是这个子系统里最廉价的伪造
- 改引文的文字会同时清除旧矩形；即使新文字仍在同一页，旧矩形也不再描述它。为避免
  新文字与未验证位置错配，文字和矩形必须分两次 PATCH；矩形更新仍要求证据已有真实
  页面定位，并通过统一的坐标形状校验。
- `kind` 和四个溯源列**不可 PATCH**，事后把人写的备注改标成模型产出，正是这些列存在的理由
- 引文匹配不到任何 chunk 是 **409 且没有强制选项**：一个无法定位引文的调用方，不该被
  提供一条"仍然当作引文存下来"的路

## 有代价的判断

**切分止于 `full_text` 的上限。** 两者一趟提取共用 400k 字符预算（约 150 页密排），
超出的部分**没有 chunk，也就无法定位**。这是真实限制，不是舍入误差。代价明摆着：
一本 700 页的书，第 300 页引不了。另一条路是每次上传都跑第二趟更大的解析，为的是服务
这个文库本来就不主要面向的文档类型。等真有人需要引第 300 页时再付这个成本，
`extraction_version` 就是那次重跑用来找旧行的钥匙。

**引文匹配不折叠大小写。** 归一化处理了 NFKC、弯引号、连字符换行、零宽字符——这些是
提取器和阅读器各自独立做的排版选择，不是作者写的内容。但大小写是内容：`quote` 断言
"论文这么说了"，拒绝的代价是重试一次,而认错页的代价是读者对全部引用失去信任。

**purge 后的来源链接与"从未链接"无法区分。** `ON DELETE SET NULL` 不留墓碑，两者都是
`paper_id: null`。这一条是实测确认而非假设的。软删除（回收站）反而能区分——链接还在，
`paper.deleted_at` 非空,正好在还能撤销的时候警告用户锚定即将失效。

**自动链接只认标识符相等，且必须唯一命中。** 标题相同不算。两行共用一个 DOI（预印本
与正式版）就拒绝链接。一个错误的链接会产出一条**自信地指向错误论文**的引用。

## 过程中挖出的两个静默陷阱

**`ADD COLUMN` 带不上 CHECK 约束。** `evidence` 的约束能生效，只因为它是**新表**——
`create_all` 建表时约束是完整的。若将来给已有表加一个带约束的列，迁移只会 `ADD COLUMN`，
结果是新装的库有约束、升级的库没有，而且**不会有任何东西报错**。已写进迁移函数的文档。

**索引也一样，但索引可以补。** `create_all` 只在建表时发 `CREATE INDEX`，所以给已有列
标 `index=True` 在新库生效、在升级库静默失效。查询依然返回正确结果，只是变成扫表——
这正是它不会被发现的原因，直到某个文库很大的人来抱怨慢。与 CHECK 不同，索引能在有数据的
表上事后创建，所以这条修掉了：新增 `_add_missing_indexes`。

**顺带修掉的 papercut：** venv 的控制台脚本 shebang 还指向改名前的 `Xuanzang` 路径，
`.venv/bin/pytest` 直接 "bad interpreter"——而那正是 AGENTS.md 让贡献者运行的命令。
23 个脚本已重指。

## 已知缺口

- **客户端界面已接入**。PDF 阅读器的文本选区菜单现在提供「保存为证据」，通过
  `Zotero.Reader.registerEventListener('renderTextSelectionPopup', …)` 扩展点工作，
  不改 reader 子模块；论文身份复用 `Zotero.Pharos.Chat.resolvePaperID()` 的 sha256
  内容寻址。矩形只对单页、合法 PDF 坐标提交；跨页选区先保存为不带矩形的引文。
- ⚠️ 维护契约：阅读器的 `pageIndex` 是 **0 基**，而 `Evidence.page_no` 与
  `Highlight.page` 是 **1 基**。当前客户端在请求边界显式执行 `+1`，后续改动不得把
  阅读器索引直接当作服务端页码。
- 没有"用户主动解除了这个链接"的记录，所以回填会把用户否掉的匹配重新链上。需要一列
  `paper_link_source`（auto / manual）
- 每日论文导入文库的路径还没接上自动链接——那是论文身份变已知的另一个时刻
