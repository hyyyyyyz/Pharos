# 阶段记录：对齐 Zotero 8.0.5 基线

目标是让 Pharos 和 Zotero **共用同一个文库**——像 Vibero 那样，两个软件不必同时开，
打开哪个都读写同一份数据。

这份文档在过程中持续更新。前序阶段见
[PHASE-PARITY-3.md](PHASE-PARITY-3.md)，数据层的方向与安全边界见
[CLIENT_DATA_ARCHITECTURE.md](CLIENT_DATA_ARCHITECTURE.md)。

---

## 为什么必须先换基线

共享文库不是配置项，是一道**单向门**。

| | userdata schema |
| --- | --- |
| 用户安装的 Zotero 8.0.5 | **123** |
| Zotero 8.0.5 源码 | **123**（已自测确认） |
| Pharos 当前客户端 | **129** |

Zotero 的迁移逻辑是"库比我旧就升级它"。如果现在让 Pharos 打开真实的 Zotero 库，
它会自动跑 124→129，**跑完之后 Zotero 8 再也打不开自己的库**——`schema.js` 在库版本
高于自身时直接拒绝。

这不是概率问题，是必然。所以顺序只能是：先把内核换到 8.0.5，再打开共享。

三份 schema 版本是**逐个实测**的，不是从文档抄来的。读真实文库时先复制了一份只读副本，
读完即删，原库未被打开。

---

## 做法：三方合并，而不是手工搬文件

拿到三棵树——**原始 10.0**（我们的旧基线，`a7cae87`）、**原始 8.0.5**（新基线，`bdd3b1d`）、
**我们改过的树**——用 git 三方合并算出精确差异。

结果远好于预期：

- **330 个文件自动合并**
- **13 处冲突**，全部是我们本来就重写过的地方（品牌、配色、启动窗口、版本号）
- 2 个文件在 8.0.5 里根本不存在（`incremental_update`、`js-build/document-worker.js`），直接丢弃

### 两个大文件用了相反的策略

| 文件 | 我们改动 | 上游 8.0.5→10.0 改动 | 做法 |
| --- | --- | --- | --- |
| `zoteroPane.xhtml` | 496 行 | 61 行 | 以我们为主。上游那 61 行全在菜单区，不触及重构区域 |
| `zoteroPane.js` | 104 行 | **1431 行** | 以 8.0.5 为底，重贴我们的 104 行 |

这个区分是有代价的判断：如果对第二个文件也"保留我们的版本"，**上游 1431 行的修复会被
整片丢掉**，而且不会有任何东西报错。

### 最大的一块不按行贴

386 行的拒绝块是把 `#zotero-trees` 包进 `pharos-deck`。按行贴必然失败——8.0.5 里那 185 行
的内部内容与 10.0 有细微差别。

改成**结构化插入**：靠标签配对计数定位 `#zotero-trees` 的开闭位置（不靠行号），把整段
原样包起来、缩进一级、后面接四个模块面板。这样完全不关心它内部是什么，8.0.5 的内容
原封不动。

## 过程中发现的两件事

### `dir_build` 带着一整套 8.0.5 用不上的机制

我们那份里有 10.0 才有的增量构建：`incremental_update`（8.0.5 没有这个脚本）、构建清单、
陈旧符号链接清理。照搬会引用一个不存在的文件。

只保留了**哈希回退**那一段——没有它，在没有 git 元数据的树里构建会直接失败。

### 子模块不是换版本，有一处是换组件

14 个子模块里 **13 个的版本不同**，而且其中一处是结构性的：

- `pdf-worker` —— 8.0.5 有，10.0 **没有**
- `document-worker` —— 10.0 有，8.0.5 **没有**

也就是说 Zotero 在这两个版本之间**替换了 PDF 处理组件**。这意味着不能只搬源码：
子模块必须整体换成 8.0.5 的 pin，否则得到的是一个内核与组件不匹配的混合体。

## 顺带修掉的一个自己的 bug

补丁被拒的一小块暴露了：早先用正则删 `showPharosGate` 时，函数删掉了、**它的 12 行文档
注释留了下来**，而且正悬在 `isFullScreen()` 上方——读起来就像是在描述那个函数。

**一段准确描述着不存在之物的注释，比没有注释更能误导人。** 已删。

## 换基线暴露的，是「我们依赖了未来的 API」

构建和测试跑起来之后，三处失败，性质相同：**我们的代码用了 10.0 才有的东西**。

### `Zotero.OSKeyStore` 不存在

token 原本经它加密后再存登录管理器。8.0.5 没有这个 API，调用直接抛异常——而且抛在
**登录那一刻**，用户无法绕过。65 个测试因它级联失败。

### `itemPaneSectionElementBase.mjs` 不存在

类在 8.0.5 里通过 `loadSubScript` 作为全局提供（`customElements.js:31`），上游自己的
`abstractBox.js` 就是直接用全局。

失败方式值得单独记：一次失败的 import 让**整个条目面板分节静默死掉**——没有标题、
没有内容，而且 `hidden` 卡在 false，于是它出现在笔记上、出现在没有 PDF 的条目上。
**一次 import 失败，表现为一个位置错误的空面板。**

### 子模块的哈希取不到

上游用 `git rev-parse HEAD` 取子模块版本，但在 monorepo 里这条命令**解析到父仓库的
HEAD**——一个每次无关提交都会变、从未对应过任何已发布产物的哈希。构建日志里它给
`pdf-worker` 请求的哈希，正是刚刚那个提交。

旧基线上的对策是算源码内容摘要。那在「没有 git 元数据」时是对的，代价是**永远命中不了
缓存、每次从源码编译**——而 8.0.5 的 reader 从源码编译还缺 `PDFJS_CONFIG`。

真正的解法是把 pin 记下来（`js-build/submodule-pins.json`）：子模块正停在官方 commit 上，
S3 产物就是按 commit 存的，验证过确实存在（reader、note-editor 均返回 200）。无 pin 时
才回落到摘要——**一个被本地改过的子模块，本来就不该去用别人编译的产物**。

## 一处真实的安全性下降，写下来而不是掩盖

token 现在按 Zotero 存自己 API key 的方式存：登录管理器，没有 OSKeyStore 那层。

**这确实更弱。** 登录管理器的密钥在 profile 里，没有主密码的话，拿到 profile 目录就能取出
token；OSKeyStore 那层还需要系统钥匙串。

换来的是与宿主应用同等的处理——同一个文库的同一类凭据，用 Zotero 自己的做法是可辩护的
下限。另一条路（拒绝在 Zotero 实际发行的版本上构建）要付出的是共享文库，也就是这个
客户端存在的理由。

能力检测保留着：基线若再往前走到有 OSKeyStore 的分支，强的那条路自动恢复。
详见 [DECISIONS.md](DECISIONS.md) §7 的修订。

顺带把那个断言「不明文存储」的测试改成断言**实际仍然成立的性质**：token 在登录管理器里、
在 Pharos 自己的 host 下、绝不落进 pref 文件。**一个断言着不再为真之事的测试，只有两种
下场：被删，或者被改成谎言。**

---

## 又一个我自己的失误

解冲突时我把 `js-build/reader.js` 判给了 8.0.5，理由是「上游基础设施跟着新基线走」——
**丢掉了我们针对无 git 元数据的适配**。是构建失败把它暴露出来的。

那条启发式判断不能一刀切：**有些「上游文件」里装着的正是我们的适配**。

## 现状

- Pharos 测试 **565 个全部通过**，与旧基线上的数字完全一致
- 两个语言文件 **678 个 id 一致**
- 上游 `itemPane` + `zoteroPane`：**153/157，三次完全相同**

新基线的上游套件**比旧基线稳定得多**。10.0 那边是 189–199 大幅波动（焦点测试在窗口未激活
时超时，个数每次都不同）；8.0.5 这两个套件共 157 个测试，稳定在 153，四个失败是同一类——
测试机语言环境是中文，citeproc 输出「不详」而测试期望 `n.d.`，与本项目无关。

**一个稳定的基线才能让比较有意义**，这对将来判断回归是实质性改善。
