# 阶段记录：对齐 Zotero 8.0.5 基线

目标是让 Pharos 和 Zotero **共用同一个文库**——像 Vibero 那样，两个软件不必同时开，
打开哪个都读写同一份数据。

这份文档在过程中持续更新。前序阶段见
[PHASE-PARITY-3.md](PHASE-PARITY-3.md)，数据层的方向与安全边界见
[CLIENT_DATA_ARCHITECTURE.md](CLIENT_DATA_ARCHITECTURE.md)。

---

## 为什么必须先换基线

共享文库不是配置项，是一道**单向门**。

| | userdata schema |
| --- | --- |
| 用户安装的 Zotero 8.0.5 | **123** |
| Zotero 8.0.5 源码 | **123**（已自测确认） |
| Pharos 当前客户端 | **129** |

Zotero 的迁移逻辑是"库比我旧就升级它"。如果现在让 Pharos 打开真实的 Zotero 库，
它会自动跑 124→129，**跑完之后 Zotero 8 再也打不开自己的库**——`schema.js` 在库版本
高于自身时直接拒绝。

这不是概率问题，是必然。所以顺序只能是：先把内核换到 8.0.5，再打开共享。

三份 schema 版本是**逐个实测**的，不是从文档抄来的。读真实文库时先复制了一份只读副本，
读完即删，原库未被打开。

---

## 做法：三方合并，而不是手工搬文件

拿到三棵树——**原始 10.0**（我们的旧基线，`a7cae87`）、**原始 8.0.5**（新基线，`bdd3b1d`）、
**我们改过的树**——用 git 三方合并算出精确差异。

结果远好于预期：

- **330 个文件自动合并**
- **13 处冲突**，全部是我们本来就重写过的地方（品牌、配色、启动窗口、版本号）
- 2 个文件在 8.0.5 里根本不存在（`incremental_update`、`js-build/document-worker.js`），直接丢弃

### 两个大文件用了相反的策略

| 文件 | 我们改动 | 上游 8.0.5→10.0 改动 | 做法 |
| --- | --- | --- | --- |
| `zoteroPane.xhtml` | 496 行 | 61 行 | 以我们为主。上游那 61 行全在菜单区，不触及重构区域 |
| `zoteroPane.js` | 104 行 | **1431 行** | 以 8.0.5 为底，重贴我们的 104 行 |

这个区分是有代价的判断：如果对第二个文件也"保留我们的版本"，**上游 1431 行的修复会被
整片丢掉**，而且不会有任何东西报错。

### 最大的一块不按行贴

386 行的拒绝块是把 `#zotero-trees` 包进 `pharos-deck`。按行贴必然失败——8.0.5 里那 185 行
的内部内容与 10.0 有细微差别。

改成**结构化插入**：靠标签配对计数定位 `#zotero-trees` 的开闭位置（不靠行号），把整段
原样包起来、缩进一级、后面接四个模块面板。这样完全不关心它内部是什么，8.0.5 的内容
原封不动。

## 过程中发现的两件事

### `dir_build` 带着一整套 8.0.5 用不上的机制

我们那份里有 10.0 才有的增量构建：`incremental_update`（8.0.5 没有这个脚本）、构建清单、
陈旧符号链接清理。照搬会引用一个不存在的文件。

只保留了**哈希回退**那一段——没有它，在没有 git 元数据的树里构建会直接失败。

### 子模块不是换版本，有一处是换组件

14 个子模块里 **13 个的版本不同**，而且其中一处是结构性的：

- `pdf-worker` —— 8.0.5 有，10.0 **没有**
- `document-worker` —— 10.0 有，8.0.5 **没有**

也就是说 Zotero 在这两个版本之间**替换了 PDF 处理组件**。这意味着不能只搬源码：
子模块必须整体换成 8.0.5 的 pin，否则得到的是一个内核与组件不匹配的混合体。

## 顺带修掉的一个自己的 bug

补丁被拒的一小块暴露了：早先用正则删 `showPharosGate` 时，函数删掉了、**它的 12 行文档
注释留了下来**，而且正悬在 `isFullScreen()` 上方——读起来就像是在描述那个函数。

**一段准确描述着不存在之物的注释，比没有注释更能误导人。** 已删。
